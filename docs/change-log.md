# Change log

Newest first. A date is the day a change landed in the repo. Public-safe from the first entry: no private paths, names or hosts.

## 2026-09-30: 1.0.1

- The websocket token stays out of the cache and out of the output. The `user` object carries, beside the API token, a `websocket_url` with a token of its own in its query; the cache file kept that address in the clear and `user info`, `api read user` and `api GET /user` printed it. `websocket_url` joins `SECRET_KEYS`: `state.merge` drops it from the cached `user` object and `redact` masks it in every JSON output. Nothing in the CLI reads the address.
- The cached `user` object loses its secret-named keys at every depth (`state.drop_secrets`): `urgent_reminder_device` carries a `device_token` one level down, which the top-level filter let through. A cache written earlier loses all three the next time a read opens that file; a file left under another cache folder or another token is never opened.
- `api --out FILE` writes the masked JSON where it wrote the reply as it came (the API token and the websocket token of `api GET /user` among it); `api --raw` alone passes a reply's bytes through untouched, by design. `workspaces show` and `workspaces logo` print through `redact` like every other printer. `TODOIST_DEBUG=1` masks secret-named values in the request it prints (a share invitation's `invitation_secret` showed). `download` sends the token to a `todoist.com` host over https only.
- `activity --since` beyond the plan's history reads from the history's edge and says so (an `--until` before that edge is refused with the reason). The API refuses such a request whole (HTTP 403 `PREMIUM_ONLY`), `--since 7d` on a 7-day plan included, and the CLI sent it after printing its own note. The README's list of API behaviour records it; the mock answers as the live API does.
- A template without `%s` in `TODOIST_TASK_URL` or `TODOIST_SESSION_URL` is a config error, as it is in the file; the first gave every task the same link, the second ended `add --src` in a traceback.
- A markdown link reads back as the full id its link carries, in any link template: the text `task#<short>` finds that id inside the link (the short id alone belongs to one project's listing and is never used when the link has the id); brackets in the text, parentheses in the link and a title after the link no longer defeat it. `--links` also reaches the lines of `move`, `order`, `reminders add` and the skip, close and update lines of `import`; `rm` names a removed task by its id alone.
- The mock follows the live API: `GET /user` answers with the whole user object; the user has a websocket address and a device token; activity beyond the history limit is refused. Two ids in the mock and the tests that were real ones, and the session id the examples used, are invented ones now.
- `__version__` is 1.0.1. It is the first version published: the `public` branch is rebuilt from this tree as one commit, tagged `v1.0.1`. 1.0.0 was built on 2026-09-29 and never left the maintainer's machine; its cache file held the API token (fixed in the entry "a task by its link, comments in full, the tree in one read" below). Tests: 75 offline OK (one new: a pasted link names its own task when two projects print the same short id), config 9, layering 5, public 1, install 2; the specs name the version and the counts as they are.

## 2026-09-30: a task named by its link

- `--links` (any verb): every task row names its task as a markdown link, `[task#<short>](<link>)`, where it printed the short id (`render.ref`, used by `line` and by the parent and subtask lines of `show`), so a row pasted into a reply opens the task. Rows without the flag are unchanged. The apps cannot search a task by its id, which made a bare id in a reply a dead end.
- `todoist.task_url` (`TODOIST_TASK_URL`): a `%s` template for a task's link, `null` by default, which keeps the app's web URL `https://app.todoist.com/app/task/<id>`. `todoist://task?id=%s` is the scheme the API documentation lists for the desktop and mobile apps ("Opens the task detail view for a given task ID", desktop 9.2.0 or later). `Item.link` applies it; `show`'s id line, the `link` JSON field and `--links` all print that one link.
- `state.task_ref` reads both printed forms back as an id: `task#<short>` and a whole markdown link `[text](<link>)`.
- The skill has a section, Name a task by its link: cite a task as the link the CLI prints, never as a bare id, and never as a link built from a short id. Tests: 74 offline OK (one new: `--links` on `list`, `add` and `show`, the template through the environment, the forms read back), config 9 (the key's validation and load), install 2, layering 5, public 1.

## 2026-09-30: a task by its link, comments in full, the tree in one read

- A task's link works wherever a task id does (`state.task_ref`, called by `resolve` and `undone`): the id is the last path segment, after a title slug if there is one (`app/task/<id>`, `app/task/<slug>-<id>`), or the `id=` of the `showTask` and `todoist://task` forms; a host without a scheme is read too. The slug form is handled by rule (the text after the last hyphen) and tested against the mock, not against a link copied from the app.
- `show --comments` prints each comment in full (the lines after the first indented under it) where it printed the first line only, and `show --comments --json` carries them as `comments` (`id`, `posted`, `content`; `file`, `reactions`, `by` where there is one), which the JSON view left out. The src/since comment stays out of both. `show` and `comments` read a task's comments through one function (`state.task_notes`: the cache for an open task, `/comments` for a completed one).
- `show ID --tree`: the task, then its subtasks in the app's order, each in full under a `# subtask N of M (depth D)` line; `--all` adds the subtasks completed in the last 89 days (one read of the completed-tasks endpoint), and the task's `subtasks:` line then counts them (`2 open, 1 done`). With `--json` the output is a list, the task first. `show ID --tree --comments` is the one call that reads a task, its subtasks and every comment.
- The cache file no longer holds the API token: the Sync `user` object carries it, and the cache stored that object whole (mode 0600, in the clear). `state.merge` now drops the secret-named keys of `user` before the cache is written, and a cache written earlier loses them on the next read; nothing read the token from there. A test proves both.
- `todos help fields` describes `comments` and the `--tree` list; the skill tells an agent to read a task the user points at with `show <id> --tree --comments`. Tests: 73 offline OK (three new: the link forms on `show`, `comments`, `add --parent`, `done`, `undone`; the tree with comments, a collaborator's comment, completed subtasks; the cache without the token), install 2, config 9, layering 5, public 1.

## Before this log

The CLI was written as a single Python 3.9 file over the Todoist API v1 Sync endpoint: the task verbs, a markdown import grammar and a generated markdown view; then subtasks, markdown bodies, an Origin link ending the body and `import --update` (an edited export applied by id); then the whole API: a verb per account object (projects, sections, labels, comments, reminders, filters, activity, user, notifications, share, views, uploads, templates, backups, emails, folders, workspaces, ids, billing), `api` for any REST endpoint, Sync command or Sync read, a cache of every resource type, plan gates before writes, and a `--yes` rule (exit 2) on destructive or bulk writes. The offline suite runs every verb as a subprocess against a local mock of the API subset the CLI uses; the live smoke runs them against a real account in a throwaway project or section; two Claude Code hooks keep the generated views current and read-only, and a skill teaches agents the vocabulary. The live API's differences from its documentation are listed in the README.
